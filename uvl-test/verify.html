Verifying a draw

Nothing on the draw pages asks to be believed. Every published claim — who entered, when the list was frozen, which drand round decided, who won — is recomputable from plain files in a public repository. The only things you have to trust are SHA-256 and the drand randomness beacon; neither belongs to us.

Three levels, by decreasing convenience: the button on a draw page (a demonstration — the page verifying itself proves little), the CLI verifier on your machine (this page, first half), and redoing everything by hand with no code of ours at all (second half).

1 · Get the files

Download the repository as an archive over HTTPS — not git clone: Git on Windows may translate line endings on checkout, which changes bytes and fails honest hash checks unless the repository's .gitattributes is respected. The archive route has no such translation.

https://github.com/constarik/uvs/archive/refs/heads/master.zip

Unpack, then in a terminal:

cd uvs-master\uvl\draws        (real draws)
cd uvs-master\uvl-test\draws   (test draws)

2 · Run the verifier

Each sealed draw folder carries the verifier snapshot frozen at seal time; the current version also sits at the site root. Either works — the script takes the draw folder as its argument:

node <draw-id>\uvl-verify-snapshot.cjs <draw-id>

Requires only Node.js — no packages, no install step, one file. It prints five steps and exits with:

exitmeaning
0every step reproduced — the published outcome follows from the published files
1MISMATCH — something published does not reproduce; that is an accusation, take it seriously
2UNVERIFIED — something could not be checked (network, missing file, round not yet published); never conflated with "checked and fine"

The verifier is deliberately outside the chain of trust — a replaced script would happily vouch for itself. It prints its version, not its own hash; if you want assurance about the script, hash it yourself and compare across sources (the frozen snapshot, the site root, the repository):

Get-FileHash <draw-id>\uvl-verify-snapshot.cjs        (Windows)
sha256sum <draw-id>/uvl-verify-snapshot.cjs           (Linux/macOS)

3 · What the five steps prove

stepclaimhow it is recomputed
1 dump chainthe captured entry dumps were not altered after capture SHA-256 of every dump file vs the hashes recorded in chain.json; the sealed link must be the last one
2 ticket listthe sealed ticket list follows mechanically from the sealed dump — nobody was added or removed by hand re-runs the parser snapshot frozen in the folder on the dump; weighted draws also re-run the frozen merge module on the frozen carry files (all hash-checked)
3 seal precedes roundthe outcome was unknowable when the list was frozen arithmetic: drand round N occurs at genesis + (N−1)·period; the seal timestamp must precede it
4 drand roundthe deciding randomness is the beacon's, not ours fetches the round from drand (4 mirrors); checks randomness = SHA-256(signature)
5 winner derivationthe published winner follows from seed + randomness + list, nothing else recomputes every ticket's score, sorts, compares rank 1 and the successor with result.json

4 · Without our verifier

Everything above can be redone with a shell and any SHA-256 tool. Hex is always lowercase; string hashes are over UTF-8 bytes with no trailing newline (printf '%s', not echo).

4.1 The derivation

combinedSeed = SHA-256( drawId + ":" + randomness )
score(id)    = SHA-256( combinedSeed + ":" + id )
ordering     = tickets sorted by score DESC; equal scores by id ASC
winner       = rank 1
successor    = first rank below the winner belonging to a DIFFERENT person
               (a person = the id before "#"; relevant for weighted draws)

drawId is the draw's folder name (also serverSeed in seal.json — it exists for domain separation only and is public from day one; all unpredictability comes from the beacon). randomness is the deciding round's, from step 4. Ticket ids are the url fields of tickets.json, in their sealed order.

4.2 Worked example

Three tickets, two persons — alice with one ticket and bob with two replicas (a weighted-draw situation):

drawId      example-draw
randomness  c8f56f8dfea73f7423e46f37a67f7b3f8bd6667bcb6d461b024e5a22b6a44f57
tickets     linkedin.com/in/alice#1
            linkedin.com/in/bob#1
            linkedin.com/in/bob#2

Expected results, byte for byte:

combined  0a2a3b2281f10d5b98159e06c35c04b2834f3eec08ba692d2869c7542a1cb045
rank 1    edd1e3079f46fe2a8591cc2e0e29e3d79d3b3ce573bd9d0bfe3b322445d03489  linkedin.com/in/bob#2
rank 2    65d13821925a8503c605ed67d4b801c1a0f75e21c3baa9f0a21f1ece59cb5bb4  linkedin.com/in/alice#1
rank 3    48c9f50f8385bfe1d5cce5ee590c36244c41e8c3664cec0247f5c858e1029eba  linkedin.com/in/bob#1

Winner: bob#2. Successor: alice#1 — rank 3 is skipped because it belongs to the winner. Recompute the combined seed yourself:

# Linux / macOS
printf '%s' 'example-draw:c8f56f8dfea73f7423e46f37a67f7b3f8bd6667bcb6d461b024e5a22b6a44f57' | sha256sum

# Windows PowerShell
[BitConverter]::ToString([Security.Cryptography.SHA256]::Create().ComputeHash(
  [Text.Encoding]::UTF8.GetBytes('example-draw:c8f56f8dfea73f7423e46f37a67f7b3f8bd6667bcb6d461b024e5a22b6a44f57'
))).Replace('-','').ToLower()

Then each rank: hash combined + ":" + id the same way.

4.3 Getting the randomness

seal.json names the deciding round (targetRound; if result.json says usedFallback, its round is the one that decided — the first available round ≥ target, a rule published at seal). Fetch it from any drand mirror, e.g.:

https://api.drand.sh/v2/chains/52db9ba70e0cc0f6eaf7803dd07447a1f5477735fd3f661792ba94600c84e971/rounds/<N>

The chain hash above is quicknet's — it is also recorded in every seal.json under drand.chainHash, and the genesis/period for step-3 arithmetic sit next to it. The beacon's randomness is by definition SHA-256 of the round's BLS signature bytes — checkable with any hash tool (hex-decode the signature first). Verifying the BLS signature itself against quicknet's public key needs a BLS library — drand's specification covers it; everything else on this page needs nothing but SHA-256.

4.4 Rebuilding the ticket list by hand

Ticket policies are versioned; a draw's policy is frozen in its seal.json under profile.tickets.policy. Policy semantics are append-only: a policy version is never redefined — changes arrive as a new version.

one-per-person (policy version 1)

Open the sealed dump (its file and hash are in seal.json). Entries are LinkedIn comment blocks, in document order, anchored on elements whose id contains replaceableComment_urn:li:comment:. For each entry the person is the first profile link (…linkedin.com/in/…) inside it, normalized to linkedin.com/in/<slug>: scheme, www., query and trailing slash dropped; locale subdomains (fr.linkedin.com…) collapsed to linkedin.com; mobile /mwlite/in/ rewritten to /in/; the slug percent-decoded and lowercased. First occurrence wins — duplicates and entries with no profile link are skipped, as are the organizer profiles listed in profile.excludes. Number the survivors TICKET-0001… in order: that must equal tickets.json.

weighted (policy version 1, spec §16.4)

Everything above yields the main-post persons; then the frozen carry files in the same folder expand them to tickets:

filerole
carry-tickets.jsonthe rehearsal draw's sealed list — every person in it is carried in automatically
carry-result.jsonthe rehearsal winner (weight 3)
uvl-merge-snapshot.jsthe expansion code, frozen at seal
weights-rule.txtthe salted rule text, revealed with the main post

All four have SHA-256s in seal.json — check them first. Weights are exclusive categories: rehearsal winner ×3, rehearsal participant ×2 (even if they also commented on the main post), main-post-only ×1. Order: main-dump persons in dump order, then rehearsal-only persons in rehearsal order; each person's replicas are consecutive ids url#1…url#w. Succession skips the winner's own replicas.

The commitment: the rehearsal draw's seal.json field ruleCommitSha256 was published before the rehearsal result existed (its git commit proves when). The main draw's seal.json copies it as carryRuleCommitSha256. Hash the frozen weights-rule.txt — it must equal both. That proves the weights were not tuned to favor anyone: the rule predates knowing who it would favor.

5 · Failure modes worth knowing

A draw page saying SEALED with no result yet is normal — the deciding round has an announced future time and nothing exists to verify until then (the ladder honestly shows two UNVERIFIED steps). Hashes failing on a git clone under Windows usually mean line-ending translation, not tampering — use the archive download. And if the verifier itself is what you doubt: the second half of this page is exactly the recipe for not using it.
